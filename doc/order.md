# اپ order؛ سفارش، رزرو موجودی و پرداخت

[بازگشت به راهنما](README.md)

این اپ سبد کاربر را به سفارش تبدیل می‌کند، موجودی را برای پرداخت موقتاً رزرو می‌کند و با تأیید سروری درگاه، سفارش را پرداخت‌شده می‌کند. API کاربر فقط سفارش‌های خودش را می‌بیند؛ پنل مدیر برای کاربران فعال با `is_staff=True` است.

## مدل‌ها و وضعیت‌ها

| مدل | داده و نقش |
| --- | --- |
| `Order` | شناسهٔ عمومی `order_id`، کاربر، مبلغ کل، هزینهٔ ارسال، مهلت، وضعیت، زمان ایجاد و شناسه‌های تراکنش/پیگیری |
| `OrderItem` | محصول، قیمت ثبت‌شده در لحظهٔ ساخت سفارش و تعداد |
| `InventoryReservation` | سفارش، محصول، تعداد رزروشده و وضعیت رزرو |

قالب شناسهٔ عمومی شبیه `Uzi-20261008-a1b2c3` است و با `id` عددی دیتابیس فرق دارد. آیتم سفارش نسخهٔ قیمت را ذخیره می‌کند؛ تغییر بعدی قیمت محصول، قیمت این سفارش را عوض نمی‌کند. نام محصول و نام دسته در خروجی آیتم‌ها همچنان از رکورد فعلی محصول خوانده می‌شوند.

| مقدار عددی | نام | رفتار پیاده‌شده |
| --- | --- | --- |
| 1 | `PENDING_PAYMENT` | وضعیت اولیه؛ فرصت پرداخت ۱۵ دقیقه |
| 2 | `PAID` | پس از تأیید موفق callback |
| 3 | `PREPARING` | تعریف شده؛ API تغییر وضعیت ندارد |
| 4 | `SENT` | تعریف شده؛ API تغییر وضعیت ندارد |
| 5 | `DELIVERED` | تعریف شده؛ API تغییر وضعیت ندارد |
| 6 | `CANCELED` | تعریف شده؛ API لغو و بازگرداندن موجودی ندارد |
| 7 | `EXPIRED` | با `expire()` برای سفارش پرداخت‌نشدهٔ منقضی؛ فراخوان فعلی آن در مسیر شروع پرداخت است |

وضعیت رزرو `ACTIVE=1` و `RELEASED=0` است. ساخت سفارش `stock` محصول را کم نمی‌کند؛ `available_stock()` رزروهای سفارش‌های وضعیت ۱ با `expires_at` در آینده را کسر می‌کند. با عبور زمان، رزرو از محاسبه کنار می‌رود حتی اگر وضعیت سفارش هنوز ۱ باقی مانده باشد. پرداخت موفق موجودی واقعی را کاهش می‌دهد و رزروها را آزاد می‌کند.

## مسیرهای API

| متد | مسیر | دسترسی / نتیجه |
| --- | --- | --- |
| GET | `/order/` | کاربر واردشده؛ آرایهٔ سفارش‌های خودش |
| POST | `/order/create/` | کاربر واردشده؛ ساخت سفارش از سبد |
| GET | `/order/<order_id>/` | مالک سفارش؛ جزئیات و آیتم‌ها |
| POST | `/order/payment/<order_id>/` | مالک سفارش؛ دریافت لینک درگاه |
| GET | `/order/payment/callback/` | عمومی؛ بازگشت درگاه و تأیید سروری |
| GET | `/manager/panel/` | staff؛ فهرست همهٔ سفارش‌ها |
| GET | `/manager/order/<order_id>` | staff؛ جزئیات سفارش؛ **بدون اسلش پایانی** |

فهرست سفارش کاربر و مدیر صفحه‌بندی ندارند. مسیر تغییر، لغو، ارسال، مرجوعی یا بازپرداخت سفارش وجود ندارد.

## ثبت سفارش از سبد

ابتدا با [cart](cart.md) واریانت دارای موجودی را به سبد اضافه کنید، سپس:

```http
POST /order/create/
Content-Type: application/json

{}
```

بدنه در این ویو خوانده نمی‌شود؛ فرستادن مبلغ، آیتم، آدرس یا هزینهٔ ارسال آن‌ها را روی سفارش تنظیم نمی‌کند.

جریان داخل یک تراکنش:

۱. بررسی می‌کند کاربر سفارش پرداخت‌نشده با مهلت معتبر دیگری نداشته باشد.
۲. وجود سبد و غیرخالی بودن آن را بررسی می‌کند.
۳. ردیف محصولات سبد را به ترتیب `id` با `select_for_update` قفل و موجودی قابل فروش را دوباره بررسی می‌کند.
۴. سفارش، آیتم‌های دارای قیمت ثبت‌شده و رزروهای موجودی را ایجاد می‌کند.
۵. مهلت را ۱۵ دقیقه بعد قرار می‌دهد و مبلغ را از مجموع قیمت × تعداد به‌علاوهٔ `shipping_cost` حساب می‌کند.
۶. آیتم‌های سبد را پاک و `201` برمی‌گرداند.

قالب پاسخ `{"message":"Order created successfully","data":{...}}` است. شیء `data` شامل فیلدهای مدل سفارش، `payment_url` و `order_items` می‌شود. برای نمونه، بخش آیتم‌ها:

```json
{
  "order_items": [
    {
      "product": {"category": "Phones", "name": "گوشی نمونه"},
      "price": 1200000,
      "quantity": 2
    }
  ]
}
```

`user` شناسهٔ عددی کاربر و `status` عدد وضعیت است. آیتم‌ها در پاسخ فعلی UUID یا `variant_name` ندارند؛ تنها نام محصول و نام دسته نمایش داده می‌شود. برای جزئیات جاری، `GET /order/<order_id>/` همین اطلاعات را مستقیم و بدون پوشش `data` می‌دهد؛ فهرست سفارش آیتم‌های تو‌در‌تو ندارد.

`payment_url` در serializer با مسیر نسبی و بدون اسلش پایانی ساخته می‌شود و ممکن است آدرس اشتباه بدهد. برای پرداخت، از `order_id` و مسیر صریح جدول استفاده کنید؛ این API با POST فراخوانی می‌شود و لینک بازکردنی مرورگر نیست.

اگر پاسخ ثبت سفارش قطع شد، قبل از تکرار درخواست، فهرست سفارش‌ها را بررسی کنید. بعد از ساخت موفق، سبد خالی شده و سفارش قبلی باید پرداخت شود.

## دریافت لینک درگاه

```http
POST /order/payment/Uzi-20261008-a1b2c3/
Content-Type: application/json

{}
```

شناسهٔ بالا را با شناسهٔ واقعی جایگزین کنید. ویو سفارش متعلق به کاربر را قفل می‌کند؛ سفارش باید پرداخت‌نشده، بدون `transaction_id` و داخل مهلت باشد. اگر مهلت گذشته باشد، `expire()` اجرا می‌شود و پاسخ `400` است.

بک‌اند مبلغ سفارش و فیلدهای `order_id`، `name`، `mail`، `desc` و `callback` را با هدر `X-API-Key` به درگاه می‌فرستد. timeout درخواست ۵ ثانیه است. با دریافت `link` از درگاه، پاسخ API:

```json
{"payment_page": "https://gateway.example/payment/session"}
```

این URL صرفاً نمونه است؛ مرورگر را به مقدار واقعی `payment_page` پاسخ هدایت کنید. مبلغ توسط سرور گرفته می‌شود و ورودی مبلغ از کلاینت پذیرفته نمی‌شود.

### تنظیم سرویس پرداخت

در [settings.py](../src/config/settings.py) مقادیر فعلی:

| تنظیم | مقدار |
| --- | --- |
| `payment_gateway_url` | `https://apis.uzicoders.ir/sandbox/gateway/payment` |
| `payment_gateway_verify_url` | `https://apis.uzicoders.ir/sandbox/gateway/payment/verify` |
| `payment_gateway_callback_url` | `http://127.0.0.1:8000/order/payment/callback/` |

کلید از `PAYMENT_GATEWAY_API_KEY` در محیط خوانده می‌شود. برای محیط واقعی باید URLها و callback مناسب آن محیط در تنظیمات پیکربندی شوند؛ متغیر env برای callback در کد فعلی وجود ندارد.

واحد پول در مدل و قرارداد داخلی نام‌گذاری نشده و تبدیل ریال/تومان انجام نمی‌شود. قیمت محصول اعشاری ولی مبلغ آیتم و سفارش عدد صحیح است؛ تا تعیین واحد و اصلاح قرارداد، قیمت‌ها را به واحد صحیح یکسان با درگاه وارد کنید و روی حفظ بخش اعشاری در سفارش تکیه نکنید.

## callback و تأیید پرداخت

درگاه به مسیری شبیه زیر برمی‌گردد:

```text
/order/payment/callback/?status=10&id=<payment_id>&order_id=<order_id>&track_id=<track_id>
```

این درخواست برای اتصال درگاه است؛ فرانت‌اند نباید صرفاً با دیدن این پارامترها خرید را موفق بداند.

- `status` به عدد تبدیل می‌شود؛ تنها مقدار `10` وارد مرحلهٔ تأیید می‌شود.
- سفارش قفل و پرداخت قبلی با وضعیت `PAID` یا وجود `transaction_id` رد می‌شود.
- `verify_payment` با بدنهٔ `{"id": payment_id, "order_id": order_id}` از سرور درگاه استعلام می‌گیرد.
- کد فعلی موفقیت را دقیقاً با `response["status"] == "100"`، یعنی **رشتهٔ** `"100"`، تشخیص می‌دهد.
- در شاخهٔ موفق، وضعیت `PAID`، شناسهٔ تراکنش برابر پارامتر `id`، مهلت `null` و رزروها `RELEASED` می‌شوند؛ موجودی واقعی هر محصول به تعداد آیتم کم می‌شود.
- پاسخ موفق `200` همان JSON دریافتی از verify است؛ redirect به صفحهٔ موفقیت فرانت‌اند پیاده نشده. قالب `payment/callback.html` نیز در این ویو استفاده نمی‌شود.

`track_id` از query خوانده می‌شود اما فعلاً روی سفارش ذخیره نمی‌شود. callback فقط وضعیت موفق پاسخ verify را کنترل می‌کند؛ کنترل جداگانهٔ مبلغ پاسخ در این کد وجود ندارد.

## پنل مدیر و تسک پس‌زمینه

`GET /manager/panel/` فیلدهای `order_id`، `total_price`، تلفن و ایمیل کاربر، `shipping_cost`، `status` و `transaction_id` را برمی‌گرداند. جزئیات مدیر از `OrderDetailSerializer` استفاده می‌کند و آیتم‌ها را نیز می‌دهد؛ queryset و serializer این مسیر در کد فعلی متصل‌اند.

Celery، ماژول `order.api.tasks` را بارگذاری می‌کند. Beat با `DatabaseScheduler` و منطقهٔ زمانی تهران، تسک `delete_expired_orders` را هر روز ساعت ۰۴:۰۰ و ۱۶:۰۰ اجرا می‌کند. این تسک سفارش‌های **از قبل دارای وضعیت EXPIRED** را که بیش از ۳۰ روز از `expires_at` آن‌ها گذشته حذف می‌کند؛ آیتم‌ها و رزروهای وابسته هم حذف می‌شوند.

این تسک سفارش pending را به expired تبدیل نمی‌کند. در حال حاضر تسک جداگانهٔ منقضی‌سازی وجود ندارد؛ تا وقتی مسیر پرداخت برای سفارش قدیمی صدا زده نشود، ممکن است وضعیت آن ۱ بماند و تسک پاکسازی آن را انتخاب نکند. برای نمایش شمارش معکوس از `expires_at` هم استفاده کنید، نه فقط `status`.

## خطاها و محدودیت‌های فعلی

| وضعیت | پاسخ |
| --- | --- |
| سبد ساخته نشده | `404`، `User has no cart` |
| سبد خالی، سفارش فعال قبلی یا موجودی ناکافی | `400` |
| پرداخت سفارش ناموجود/دیگری | `404` |
| سفارش منقضی یا غیرقابل پرداخت | `400` |
| اتصال ناموفق در شروع پرداخت یا نبود لینک در پاسخ | `502` |
| callback با status نادرست، پرداخت تکراری یا verify ناموفق | `400` |
| خطای اتصال verify یا خطای داخلی callback | `500` |

سهمیه‌ها: خواندن سفارش‌ها ۶۰ در دقیقه، ساخت سفارش ۵ در دقیقه، شروع پرداخت ۵ در دقیقه، callback بیست در دقیقه و جزئیات مدیر ۶۰ در دقیقه. فهرست مدیر throttle صریح ندارد.

محدودیت‌های مؤثر بر استفاده:

- آدرس سفارش، محاسبهٔ ارسال، کد تخفیف و چرخهٔ ارسال پیاده نشده‌اند؛ `shipping_cost` در ساخت فعلی صفر می‌ماند.
- callback مهلت یا کافی بودن موجودی را دوباره بررسی نمی‌کند و فقط سفارش پرداخت‌شده/دارای transaction را رد می‌کند؛ رسیدن پرداخت پس از انقضای رزرو نیازمند اصلاح منطق پیش از بهره‌برداری واقعی است.
- ساخت سفارش دوباره `show` و واریانت بودن آیتم‌های موجود سبد را کنترل نمی‌کند.
- محدودیت «یک سفارش فعال» بررسی در سطح ویو است و قفل جداگانه‌ای روی کاربر ندارد؛ درخواست‌های هم‌زمان ساخت سفارش را در کلاینت تکرار نکنید.
- `order_id` با دو ذخیره و بررسی یکتایی روی بخش خام شناسه تولید می‌شود؛ این بخش در شرایط هم‌زمانی نیازمند بازبینی است.
- آیتم خالی در callback با `list(None)` به خطای داخلی می‌رسد. کم کردن موجودی نیز با update مستقیم است و کش محصول را خودکار باطل نمی‌کند.
- حذف واقعی محصول یا کاربر به‌علت روابط CASCADE می‌تواند سوابق سفارش را حذف کند؛ مخفی کردن محصول از API با حذف رکورد در admin تفاوت دارد.
- مسیر بازپرداخت یا مدیریت اختلاف پرداخت وجود ندارد؛ این سند توصیف کد فعلی است و اتصال عملی درگاه باید جداگانه آزمایش شود.
